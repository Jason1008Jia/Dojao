01

产品定位与核心价值

一句话：不是又一个数据库，也不是又一个 BI 报表工具，而是「数据不动、计算汇聚」的分析平台 —— 原生带一个懂数据、会动手的 AI 分析师。

数据不搬家核心

订单在 MySQL、库存在 PostgreSQL、流水在 ClickHouse —— 一条查询直接跨库分析， 不需要先建数仓、不需要每晚抽数同步。减少一条数据链路，就少一份不一致与运维成本。

会动手的 AI 分析师差异化

说人话就能问数：AI 自动找表、生成并执行只读查询、画图、导出文件、解释结论。 涉及改表等写操作时，必须由你点头确认。

大查询也能跑完稳定性

内存吃紧时自动把中间结果落到磁盘继续计算，而不是直接报错。 优先保证「按时拿到结果」，单条查询出问题也不拖垮整个集群。

开箱即用一个安装包即可在本机跑起来，个人分析无需申请集群；团队要扩再横向加机器。
一种语法，所有数据源统一命名与统一的 SQL 体验，跨源关联像查一张表。
过程看得见每一步在做什么、跑到哪、占多少资源，界面实时可见，随时可以叫停。
安全可控默认只读、写操作人工确认、按角色授权、数据按账号隔离。
02

产品架构：一张图看懂它如何运转

用户从网页、命令行或常用 BI / 数据库工具进入；AI 助手帮助把问题变成查询；调度中心负责规划并把计算分发给多台机器； 底层直接连接各类数据源。用户只看到「提问 → 结果」，中间过程被产品隐藏。

两个产品级取舍

AI 只负责「理解」，执行交给引擎。模型换代、切换供应商，都不会影响查询结果的正确性； 执行过程始终可复现、可审计。

中间结果不回流中心节点。分布式计算在计算节点之间完成，中心只做调度与结果汇总 —— 大查询不会把中心节点压垮，集群越大收益越明显。

同一个产品，三类角色各取所需：业务同学用自然语言直接问数，分析师用 SQL 精细加工，管理员守住数据与集群边界。

业务分析师零门槛

不会写 SQL 也能问：「上个月各区域销售额同比如何？」 系统自动找表、生成查询、画图并给出结论，结果可一键导出。

数据工程师 / 分析师高效率

多标签 SQL 工作台、脚本保存、结果转置与导出；复杂多表关联、窗口函数、分组聚合， 一条 SQL 直连多个业务系统。

管理员 / IT可控

账号与角色隔离、集群资源看板、任务随时可停； 新数据源以插件方式接入，不需要改动计算引擎。

典型场景

跨系统经营分析订单在 MySQL、库存在 PostgreSQL、流水在 ClickHouse —— 一条查询合并分析，不用先建数仓、不用每晚抽数。
自助式问数业务同学直接在对话框提问，省去「提需求 → 排期 → 出报表」的往返。
大促 / 月结等大查询数据量大、内存吃紧时自动落盘继续跑，优先保证按时出结果。
临时取数与交付结果直接导出 Excel / CSV / PDF / 图片，或把查询保存为脚本，下次复用。

06

AI 能力：把「一句提问」直接变成「可交付的结论」

这不是一个聊天窗，而是一名会动手的分析师：它理解问题、自己去找数据、写查询、先试跑验证、画图、讲结论， 最后把结果变成可以直接转发的文件。数据和执行始终在引擎里，AI 只负责「把分析做对、把结论讲清楚」。

听得懂理解

从一句业务话里识别指标、维度、时间范围与口径；上下文里追问「按区域拆一下」，它知道接着上一问继续，而不是从头再来。

找得到动手

先查有哪些数据源、表、字段和函数，再写 SQL；不臆造表名，也不靠猜字段。跨数据源关联与分析同样一句话完成。

交得出交付

结果自动选图、解释趋势与异常，并能一键导出为表格、图片、PDF 或带交互图表的网页报告，直接用于汇报。

它是怎么工作的：一轮「思考—动手—看结果」的循环

AI 不是一次性把 SQL 猜出来，而是像分析师一样边做边验证：每一步先想清楚要查什么，调用一个工具拿到真实结果，再决定下一步。 整个过程对用户可见 —— 思考过程、生成的 SQL、查询结果都实时流式展示，随时可以叫停。

步骤它在做什么用到什么用户看到什么
1 · 理解识别指标、维度、时间与口径，判断要不要追问推理内核 + 上下文思考过程流式输出
2 · 找数列出数据源、表、字段与函数，确认数据是否存在数据探查工具「正在查看 orders 表…」
3 · 写查询按目标库方言生成只读 SQL上下文工程可展开的 SQL 卡片
4 · 试跑先在引擎里跑一遍，验证列名、口径与结果规模execute_sql结果预览与耗时
5 · 纠错报错或结果不符时改写重试，而不是把错误抛给用户推理内循环自动纠正轨迹
6 · 交付选最合适的图表，讲趋势与异常，生成可下载文件render_chart / export_file图表 + 结论 + 下载按钮
多轮追问不丢上下文同一会话里可以连续追问「那华东呢」「按周看」，上一轮结果会被复用。
结果引用免重算已经查过的结果会带一个引用（如 rs3 / last），画图和导出直接复用，不重复提交查询。
自动收敛单轮推理最多 16 步，通常 3~6 次工具调用就给出结论，不会无止境试探。

13 个内置工具：AI 的能力边界，就是工具边界

AI 能做什么，不由模型「自由发挥」决定，而是由它被授予的工具决定。工具集按账号角色裁剪：分析师拿不到集群诊断类工具，开发者 / 管理员才可见。

类别工具它能做到什么
数据探查 list_catalogs · list_tables · describe_table · describe_function 有哪些数据源、库表、列定义与可用函数（含自己的 UDF），先看清楚再写查询。
取数执行 execute_sql 执行只读 SQL（SELECT / SHOW / DESCRIBE / EXPLAIN），返回列名与结果预览；可附带真实耗时用于性能对比。
变更结构 execute_ddl CTAS、创建 / 删除数据源、创建 / 删除函数、删表、清空表；执行前必须由用户在界面上确认。
可视化 render_chart 把结果直接画在回答里，支持 11 类二维图表与「柱状 + 折线」混合图、双 Y 轴。
交付 export_file 导出 md / txt / html / csv / excel / png / jpg / pdf，生成后回答下方出现下载按钮。
诊断 cluster_status · read_logs · list_queries · query_status · operator_status 仅管理员 / 开发者可见：看集群负载、节点日志、查询列表与算子级指标，回答「为什么慢 / 为什么失败 / 卡在哪台机器」。
分析师角色会被自动剔除上述 5 个诊断工具，即使技能白名单里写了也不会下发；角色边界优先于任何提示词。

上下文工程：让 AI 懂业务、懂方言、懂函数

它每次都被「交代」了什么

  • SQL 方言：当前连接的数据源语法差异，生成的查询直接可跑。
  • 函数目录：内置函数 + 当前账号可见的 UDF 清单，不必检索，也不许臆造函数名。
  • 角色与边界：当前账号能用哪些工具、哪些话题不该回答。
  • 场景技能：把「常用分析套路 + 允许的工具子集」打包成技能，业务同学选中场景即可开始。

模型与上下文

AI 的能力来自「模型 + 企业上下文」两层：模型可以替换，上下文由产品持续沉淀。

模型可替换可对接任意兼容主流协议的大模型服务，按账号配置，不被单一供应商锁定。
结果可追溯每一步分析、生成的 SQL、拿到的结果与图表都在会话中留痕，可回看、可复核。

下一步：让 AI 真正懂「这家企业」近期规划

执行层已经就绪；下面三项是把「AI 会查数」变成「AI 懂业务」的关键。它们都与执行引擎解耦，升级知识不会影响计算结果。

语义层v0.2

把业务描述、同义词与指标口径沉淀为可维护的定义：让 AI 知道「GMV」「活跃用户」在本企业到底怎么算，不只靠字段名猜。

  • 指标口径：含不含退款、按什么时间粒度统计。
  • 同义词与别名：一线叫法映射到物理字段。
  • 回答可解释：说明本次用的是哪套口径。

企业知识库规划

把制度文档、数据字典、历史分析与常见问题接入 AI 的检索范围；回答前先查企业自己的资料，而不是只靠通用常识。

  • 业务规则：回答时标注依据了哪份文档、哪一条。
  • 数据字典：表 / 字段的业务含义与使用禁忌。
  • 分析沉淀：复用团队已有的分析方法与历史问答。

数据血缘规划

理解表与字段之间的上下游关系：一个指标由哪些表加工而来、改一张表会影响哪些报表与指标，让「数从哪来、改了会怎样」有据可查。

  • 来源追踪：「这个数从哪来」可一路看到上游。
  • 影响分析：「改这张表会影响谁」提前暴露。
  • 归因辅助：异常时顺着血缘找根因，而不是盲查。
语义层进入 v0.2；企业知识库与数据血缘随后续版本逐步落地。三者共同构成 AI 的「企业上下文」，让回答从「查得到」升级为「答得对、说得清、改得稳」。

安全护栏：能干活，但不越界

对数据与集群的保护

  • 默认只读：取数工具只接受 SELECT / SHOW / DESCRIBE / EXPLAIN；写操作走单独的 DDL 工具。
  • 写操作人工确认：建表、删表、改函数等必须先由用户点击确认，AI 不能自行提交。
  • 行数硬上限：AI 提交的查询自动加 LIMIT 500，图表取数最多 200 行，避免拉全表撑爆界面。
  • 集群繁忙保护：重查询前先看集群负载；繁忙时自动拒绝并建议稍后重试，不把集群压垮。

对角色与过程的约束

  • 按角色授权：集群、日志、算子诊断 5 个工具只对管理员 / 开发者开放，分析师不可绕过。
  • 数据按账号隔离：会话、结果缓存、导出文件互相不可见。
  • 自动收敛：单轮推理最多 16 步，同一问题不反复执行等价查询。
  • 随时可停：一键中断推理与查询，后台资源立即释放。

典型场景

经营分析问答「本月各渠道 GMV 环比」一句话出数、出图、出结论，业务同学不必等排期。
跨系统对数 / 对账订单在 MySQL、流水在 ClickHouse，一条 SQL 直接比对两边金额与笔数差异。
异常归因从总盘下滑一路下钻到区域、渠道、商品，AI 连续追问并逐步缩小范围。
开发者排障查查询列表、看算子阶段与节点日志，回答「这条查询为什么慢、卡在哪个 Worker」。
能力边界

AI 不直接改数据结构，也不替用户做业务判断。它负责把「怎么查」做对，把口径与假设说清楚； 指标口径的最终解释权仍在业务方。涉及写入与删除的操作，一律需要人工确认。

07

大查询保障：优先「跑完」，而不是「跑得快」

大查询最常见的失败不是慢，而是内存不够直接报错。产品把「内存不够」变成「先落盘、再继续」—— 宁可多花一点时间，也要把结果交到用户手上。

内存不够时会发生什么

  • 自动落盘：中间结果超出内存预算时，自动写入本地磁盘，继续计算。
  • 边算边减压：窗口 Top-N、分组聚合等场景动态压缩中间状态，内存占用不随数据量线性增长。
  • 读得慢一点：下游消费变慢时自动放慢读取节奏，给落盘留出追赶时间，而不是直接崩溃。
  • 多盘与保护：支持多块磁盘轮转写入；磁盘写满时安全中止，不影响节点上其它任务。

对用户意味着什么

  • 结果确定性：同样的查询在内存紧张时也能给出同样正确的结果。
  • 故障隔离：单条查询资源超限只影响它自己，不会把整台机器拖死。
  • 可预期的成本：磁盘落盘有总量上限，不会悄悄写满整块盘。
  • 可观测：看板实时显示落盘趋势，容量规划有据可依。

覆盖常见的大查询形态

分组聚合高基数分组、去重统计的中间状态可落盘，内存峰值不随分组数线性增长。
窗口分析超大分区的排序与排名可落盘；Top-N 场景先裁剪再计算。
大表关联两侧数据都很大时也能完成关联，不因一侧装不进内存而失败。
排序与去重超出内存的数据自动分段排序后归并，结果保持稳定。
产品取舍

慢一点，但一定给出答案。对经营分析、月结、大促复盘这类「结果必须按时交付」的场景， 我们优先保证完成率，而不是极限速度。需要极致性能的固定报表，仍建议沉淀到数仓。

路线图与下一步

先把「能问、能算、能交付」做扎实，再逐步降低使用的门槛与不确定性。

现在可用

  • 9 类数据源的联邦查询
  • 自然语言问数 + 图表 + 导出
  • SQL 工作台与脚本沉淀
  • 任务 / 集群监控与随时停止
  • 单机与集群两种部署

近期（v0.2）

  • 语义层：补业务描述、同义词与指标口径，让 AI 更懂业务。
  • 执行前护栏：先评估成本与集群负载，再决定是否执行。
  • 错误自修复：针对常见错误自动纠正并重试，减少人工介入。
  • 效果评测：用标准问题集量化问数准确率与改进幅度。

中期方向

  • 企业知识库：接入制度文档、数据字典与历史分析，回答带引用来源。
  • 数据血缘：表 / 字段上下游与影响分析，回答「数从哪来、改表影响谁」。
  • AI 能力服务化：命令行、JDBC 与二次开发均可复用。
  • 运行轨迹与成本看板：token、耗时、采纳情况可量化。
  • 团队协作：查询与结论的分享、复用与沉淀。
  • 数据源扩展：消息队列、搜索、文档库、数据湖。

衡量成功的四个指标

问数采纳率AI 给出的查询与结论被直接使用的比例。
首答成功率第一次提问就得到可执行结果的比例。
大查询完成率资源紧张场景下仍能按时返回结果的比例。
周活跃分析用户每周至少完成一次分析的用户数。
一句话总结

让每个业务问题都能用一条查询回答 —— 而答案可解释、可复现、可交付。
