# Dojao AI 能力现状与演进规划

> 范围：本文总结当前 Dojao 内置 AI 数据分析助手（`dojao-ai` + `dojao-ui/ai`）已经具备的能力、
> 现存短板，以及下一版本（v0.2 起）的演进方向与落地阶段。
>
> 定位判断：查询引擎稳定之后，AI 不应下沉进优化器/执行器，而应进化为**引擎上方的语义层 + Agent 控制面**。
> 引擎负责“稳定、可观测地执行 SQL”；AI 负责“理解问题、组织上下文、编排工具、校验结果”。

---

## 一、当前能力（v0.1）

### 1.1 分层架构

| 层 | 模块 | 职责 |
| --- | --- | --- |
| 通用推理内核 | `dojao-ai` | 手写 ReAct 循环、流式事件回调、LLM 接入。零 `dojao-metastore` / `dojao-ui` 依赖 |
| 业务绑定层 | `dojao-ui/ai` | 构造 13 个工具、系统提示词、角色与技能、会话/配置/文件存储、HTTP 流式端点 |
| 引擎能力 | `dojao-server` / `dojao-metastore` | 查询提交与监控、元数据、集群状态、日志、算子指标 |

`dojao-ai` 的分层是当前最大的架构资产：推理内核与 Dojao 业务解耦，后续可以平移到服务端或其他入口。

### 1.2 推理内核（`ReActAgent`）

- **ReAct 循环**：思考 → 工具调用 → 观察 → 再思考 → 结论，单轮最多 16 步。
- **全链路流式**：正文（`onText`）、推理模型的思考流（`onThinking`）、工具调用（`onToolCall`）、
  工具结果（`onToolResult`）、完成/错误事件，实时推给前端展开轨迹。
- **防死循环**：
  - 工具调用签名去重，完全相同的调用不重复执行；
  - 步数用到约 2/3 时注入“尽快收敛”提示；
  - 步数用尽后**禁用工具再调一次模型**，强制基于已有观察给出最终回答。
- **上下文保护**：单条工具结果超过 4000 字符截断；单轮 LLM 调用超时 120 秒。
- **长对话**：支持传入历史消息，保持多轮上下文。

### 1.3 模型接入与配置

- 通过 LangChain4j 的 **OpenAI 兼容流式端点**接入（`OpenAiStreamingChatModel`），可对接
  OpenAI / DeepSeek / 任意兼容网关。
- 配置按账号隔离，持久化在 UI 的 SQLite（`ui_ai_config_user`，一账号一行）；
  未配置的账号回退管理员配置；默认值为 DeepSeek 兼容端点。
- 另有最小化的单轮同步服务 `AiChatService`（非流式），作为早期里程碑保留。

### 1.4 工具矩阵（13 个）

| 工具 | 能力 | 关键边界 |
| --- | --- | --- |
| `execute_sql` | 执行只读 SQL 并返回结果预览 | 只放行 SELECT / WITH / SHOW / DESCRIBE / EXPLAIN；自动加 `LIMIT 500`；可附带引擎墙钟耗时 |
| `execute_ddl` | 变更库表结构 | 仅 CREATE / DROP / ALTER / TRUNCATE；**执行前必须由用户在界面确认**，确认回调缺失则一律拒绝 |
| `render_chart` | 把查询结果渲染成网页图表 | 11 种图表；结果最多 200 行；可复用 `execute_sql` 的结果集引用（如 `rs3` / `last`），避免重算 |
| `export_file` | 导出可下载文件 | md / txt / html / csv / excel / png / jpg / pdf；纯 Java 实现，无第三方依赖 |
| `list_catalogs` | 列出数据源 | — |
| `list_tables` | 列出 catalog / schema 下的表 | — |
| `describe_table` | 查看表列定义 | — |
| `describe_function` | 查看函数详情 | 函数清单已前置注入提示词 |
| `cluster_status` | 集群资源与负载 | 提交重查询前的负载判断依据 |
| `read_logs` | 查看 Master / Worker 日志尾部 | 只读；远端 Worker 依赖 Master → Worker 免密 ssh |
| `list_queries` | 查询任务列表 | 支持状态筛选 |
| `query_status` | 单查询完整状态与算子 DAG | 含行/字节/内存/溢写/CPU/速率 |
| `operator_status` | 单算子指标与各 Worker 任务 | 可下钻到任务级失败原因 |

角色控制：`cluster_status` / `read_logs` / `list_queries` / `query_status` / `operator_status`
属于开发者工具，分析师角色会被剔除，并在提示词中明确拒绝相关话题。

### 1.5 上下文与提示词工程

系统提示词是当前 AI 效果的核心，已包含：

- **引擎能力与边界**：分布式定位、磁盘溢写兜底、联邦查询、自动优化、支持的语句、暂不支持的语法
  （SEMI JOIN / CROSS JOIN / INTERSECT / EXCEPT 等）。
- **方言约定**：单引号字符串、三段式表名、保留字、LIMIT OFFSET、CASE 必须搜索式、JOIN 必须带 ON、
  JSON / UNNEST、窗口函数限制、类型名等。
- **全部可用 SQL 函数清单**（内置 + 当前用户可见 UDF），避免模型臆造函数。
- **HTTP 接口清单**：让模型能如实回答“调哪个接口”，并明确它自己不能发起 HTTP 请求。
- **角色提示词**：admin / developer / analyst 的能力与话术隔离。
- **输出规范**：GFM Markdown、先结论后展开、不重复工具过程。
- **技能（Skill）**：用户可定义“追加提示词 + 工具白名单”，复用特定分析场景。

### 1.6 会话、产物与交互

- **长对话会话**：按用户隔离持久化（`ui_ai_session`），一轮 = 用户问题 + 助手回答 + 工具名列表。
- **图表**：11 种二维图表；支持混合图、双 Y 轴；前端直接渲染。
- **文件导出**：8 种格式；xlsx 用最小 OOXML 直接写、PDF 用 Java2D 位图装进最小 PDF 结构。
- **交互控制**：DDL 确认（`/api/ai/confirm`）、强制停止（`/api/ai/stop`）、参考文件解析
  （`/api/ai/files/parse`）、导出文件下载（`/api/ai/files/{id}`）。
- **流式协议**：NDJSON 事件：`text` / `thinking` / `tool_call` / `tool_result` /
  `ddl_confirm` / `chart` / `file` / `done` / `error`。

### 1.7 安全与边界（当前已有）

- `execute_sql` 首关键字白名单（只读）；写操作只能走带人工确认的 `execute_ddl`。
- 查询结果自动 `LIMIT 500`，结果集预览 50 行，图表 200 行，日志最多 1000 行。
- 集群繁忙（槽位 ≥ 90% 或 CPU ≥ 80%）时自动拒绝重查询，避免打爆集群。
- 按账号隔离模型配置、会话、导出文件；角色决定工具集。
- 提示词层面禁止越界话题、禁止臆造 URL / 函数名 / 表名。

### 1.8 现有测试

`dojao-ui/src/test/.../ai` 下已有大量行为级探针测试，覆盖：只读 SQL 守卫、提示词边界、
引擎能力、图表规格、集群感知、方言提示、引擎可见性、文件导出、文件解析、函数检索、
角色权限、行数上限、会话存储、技能组合、耗时提示、轮次结构等。
`dojao-ai` 也有 ReAct 循环与单轮服务的探针测试。

这些测试保证“规则不被改坏”，但**不是 NL → SQL 的准确率评测**。

## 二、当前局限

1. **AI 被“困”在 Web UI**
   - 推理运行时、工具绑定、系统提示词全部在 `dojao-ui`。
   - CLI、JDBC、二次开发、其他系统无法复用 AI 能力；UI 是唯一入口。

2. **语义上下文薄**
   - 只有 catalog / schema / table / column 的结构信息，没有业务描述、同义词、指标口径、表间关系、
     示例值、已验证查询。
   - 模型需要靠多轮工具试探“摸清”库表，token 成本高、准确率不稳定。
   - 函数清单全量注入，库表信息却按需探查，上下文策略不对称。

3. **执行前缺少强制的成本护栏**
   - “先 EXPLAIN、看负载、再执行”目前只是提示词约定，没有服务端强制。
   - 自动 `LIMIT 500` 只控制返回行数，不控制扫描量 / 计算量。

4. **自修复是提示词级别的**
   - “报错后改正再试”依赖模型自觉；没有服务端限次、错误分类、针对性回灌 schema 的机制。

5. **没有评测闭环**
   - 缺少 golden set（自然语言 → SQL / 期望结果）与执行结果级判定。
   - 提示词或模型任何改动都无法量化“变好还是变坏”。

6. **缺少一等公民的运行轨迹**
   - 工具调用、SQL、token、耗时、成本、用户是否采纳，没有结构化落库与回放。
   - 只有会话轮次，难以做成本分析、失败归因和持续优化。

7. **模型接入单一**
   - 仅 OpenAI 兼容对话模型；没有嵌入模型、重排、本地模型路由，也没有语义缓存。

## 三、下一版本（v0.2）目标

### 3.1 总目标

把 AI 从“一个会调工具的聊天助手”升级为**引擎上方的语义控制面**：

1. **更懂数据**：语义元数据 + 检索式上下文；
2. **更可控**：执行前成本评估、限次自修复、明确预算；
3. **可复用**：Agent 运行时服务化，UI / CLI / 二次开发共用；
4. **可度量**：评测集 + 运行轨迹，让每次改动都有数据依据。

### 3.2 非目标（明确不做）

- 不把 LLM 塞进查询优化器 / 执行器；
- 不在没有评测集之前做模型微调；
- 不为“看起来先进”而引入多 Agent 互聊编排；
- 不在需求未验证前做引擎内向量索引 / 语义算子。

## 四、v0.2 工作项

### P0-1 语义层（最高优先级）

新增/扩展语义元数据能力（可落在 `dojao-metastore`，或独立 `dojao-semantic`）：

- 表 / 列：业务描述、同义词、单位、枚举值、示例值、是否敏感；
- 表间关系：join graph（等值键、基数、推荐 join 路径）；
- 指标注册表：指标名、口径 SQL、维度、时间粒度；
- 已验证查询：自然语言问题 + 标准 SQL + 适用范围 + 创建人；
- **上下文检索接口**：输入用户问题与权限，返回 Top-K 相关表 / 列 / 指标 / 历史查询，
  而不是把全库 schema 塞进提示词。

验收标准：

- 系统提示词不再依赖“逐表试探”即可获得主要 schema；
- 在 golden set 上，多表问题的执行准确率相对当前基线有可量化提升；
- 上下文 token 数下降或持平。

### P0-2 评测体系（与 P0-1 并行）

- 定义 golden set 格式：`question`、`setup SQL`、`expected SQL`、`expected result`、`tags`、`difficulty`；
- 评分以**执行结果一致**为主（列集合 + 值集合，允许排序无关），辅以 SQL 结构检查；
- 提供本地运行脚本与 CI Job；每次模型 / 提示词 / 工具改动输出对比报告；
- 建立基线：单表查询、多表 JOIN、聚合、窗口、跨源对数、歧义澄清等分桶统计。

验收标准：

- CI 能在 PR 上给出准确率、失败用例清单；
- 任何提示词调整都能看到分桶指标的升降。

### P0-3 Agent 运行时服务化

当前 `AiAgentService` 绑定在 UI，建议：

- 保持 `dojao-ai` 纯内核不变；
- 抽出 `SqlExecutor` / `MetadataProvider` / `ClusterProbe` 等 SPI，把业务 Agent 从 `dojao-ui`
  移到新模块（如 `dojao-agent`）；
- 在 `dojao-server` 暴露 Agent 入口（Flight Action 或 HTTP 流式），UI 退化为一个客户端；
- CLI / 二次开发 / 其他系统可复用同一套提示词、工具与安全规则。

验收标准：

- 同一 AI 能力可被 UI 与至少一个非 UI 客户端调用；
- 提示词、工具、权限逻辑只有一份实现，不复制。

### P1-1 运行时硬化

- **EXPLAIN 先行**：执行前统一 `EXPLAIN`，基于计划估算扫描量 / 连接规模 / 是否可能溢写；
  超过阈值时拒绝、改写或要求用户确认；
- **限次自修复**：对语法错误、未知列、类型不匹配、暂不支持语法分类，回灌错误 + 相关 schema，
  最多重写 1~2 次；禁止重复提交相同 SQL（内核已有去重，需扩展到“语义等价”）；
- **预算**：步数、token、工具结果字符、结果行数、墙钟时间、成本上限统一配置与透出；
- **确定性管线**：把高频场景（快速查数、跨源对数、报告生成）固化为固定步骤的 recipe，
  LLM 只负责歧义消解与文案，不负责流程控制；
- **语义缓存**：问题归一化 + schema 指纹 → 已验证 SQL；SQL 归一化 → 结果缓存（带 TTL）。

### P1-2 运行轨迹与可观测性

- 每次 Agent 运行落一条结构化 Trace：`runId`、用户、问题、模型、token、工具调用序列、
  SQL、结果行数、错误、耗时、DDL 审批结果；
- 提供查询 / 回放 / 统计接口与页面：成功率、平均步数、平均 token、失败原因分布、成本；
- 与引擎 `queryId` 关联，能从一次 AI 回答直接跳到对应查询的算子指标。

### P2 主动化与治理

- 定时 / 事件触发的 Agent：数据质量巡检、异常检测、日报 / 周报生成；
- 审批流：DDL 之外，导出敏感数据、订阅告警也需要确认；
- 权限：RBAC + 行级 / 列级权限在**引擎侧**强制，不依赖提示词；
- 提示词注入防护、PII 脱敏、结果脱敏、审计日志。

## 五、落地阶段

### 阶段 0：地基

- 确定语义元数据 schema 与 SPI 边界；
- 搭好 golden set 与评测脚本，记录当前基线；
- 不改用户可见行为。

### 阶段 1：语义增强

- 语义元数据录入与检索接口；
- 提示词从“全量清单”改为“检索结果 + 关键约束”；
- 接入已验证查询与指标口径；
- 评测报告进入 CI。

### 阶段 2：服务化与硬化

- 抽出 `dojao-agent`，UI 改为客户端；
- EXPLAIN 先行、限次自修复、预算控制；
- Trace 落库与成本看板。

### 阶段 3：主动化与治理

- 定时任务 / 异常检测 / 报告生成；
- 审批流、审计、行级权限；
- 视需求评估引擎内 AI 原生能力（向量索引、AI 函数）。

## 六、建议验收指标

| 维度 | 指标 | 建议目标（首版） |
| --- | --- | --- |
| 准确率 | golden set 执行一致率（单表） | ≥ 85% |
| 准确率 | golden set 执行一致率（多表 / 聚合） | ≥ 65% |
| 安全 | 越权 / 写操作被拦截率 | 100% |
| 安全 | 跨用户数据泄漏 | 0 |
| 稳定性 | Agent 运行失败可归因率 | 100%（有 Trace） |
| 成本 | 单次问答平均 token / 工具步数 | 相对基线下降或持平 |
| 体验 | 首 token 延迟、整轮 p95 耗时 | 持续监控，不劣化 |

指标是护栏，不是 KPI；先建立基线，再谈优化。

## 八、原则与反模式

**保留并强化**

- 手写 ReAct 内核 + 流式事件：可控、可观测、兼容性好；
- 工具抽象与业务解耦；
- DDL 人工确认、只读白名单、自动行数上限、角色隔离；
- 系统提示词中“引擎能力边界 + 方言约定”的显式表达。

**避免**

- 在没有评测集时调提示词或微调模型；
- 把全量 schema / 全量函数清单当成“上下文”；
- 用多 Agent 编排替代确定性的流程控制；
- 让 LLM 直接决定是否执行高风险操作；
- 把 AI 能力锁死在单一 UI 入口；
- 在引擎层过早引入 LLM 依赖，破坏引擎的确定性与可观测性。
